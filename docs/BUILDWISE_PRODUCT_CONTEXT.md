# BuildWise AI

## 프로젝트 정의

BuildWise AI는 업무 조건과 기존 AI 솔루션을 비교해

- 기존 솔루션 활용
- 기존 솔루션 + 보완
- 추가 개발 검토

중 어떤 방향이 적절한지 판단하도록 돕는
AI 도입 의사결정 지원 도구다.

단순 AI 툴 추천 서비스나 가격 비교 서비스가 아니다.

핵심 질문은:

> “우리 업무에서 어디까지 기존 AI를 쓰고,
> 어디부터 보완하거나 새로 만들어야 하는가?”

이다.

## Vision

AI 활용의 차이는 ‘얼마나 많이 쓰느냐’가 아니라
‘우리에게 무엇이 필요한지 정확히 아느냐’에서 시작된다.

업무마다 흩어진 선택을 기준으로 만들고,
그 기준을 쌓아 전사적인 AI 활용 체계로 확장한다.

BuildWise는 그 판단을 돕는다.

## 넓은 Persona

업무에 AI 활용을 검토하고,
도입 방식까지 판단해야 하는 기업 실무자와 의사결정자.

특정 직무만을 위한 제품이 아니다.

## PoC Persona

반복적인 프로젝트 문서 검토 업무에
AI 활용을 검토하는 HIMEC PM·CM 실무자.

## Pain Point

현재 AI 도입 판단은 다음과 같이 흩어져 있다.

```
업무 문제 발생
→ AI 검색
→ 여러 솔루션 발견
→ 가격·기능·한도 개별 확인
→ 다시 비교표 작성
→ 부족 기능 확인
→ 구매/보완/개발 여부 논의
```

이 과정에서 생기는 핵심 문제는:

1. 판단 기준이 담당자마다 다르다.
2. 기존 솔루션으로 가능한 기능까지 다시 개발할 수 있다.
3. 한 번 조사한 결과가 조직의 기준으로 축적되지 않는다.

핵심 문제는 AI가 부족한 것이 아니라,
우리 상황과 기존 AI 사이의 Gap을 판단할 기준이 없다는 것이다.

## Decision Framework

BuildWise의 공통 판단 기준:

- 현재 해결하려는 업무
- 업무 규모
- 사용할 수 있는 비용
- 반드시 필요한 기능
- 허용할 수 없는 제약조건

기존 솔루션에서 비교할 정보:

- 비용
- 사용 범위와 한도
- 제공 기능
- 제약조건
- 도입 조건

판단 과정:

```
우리 업무 조건 정의
→ 기존 솔루션 구조화
→ 조건 매칭
→ 충족 / 미충족 Gap 확인
→ 기존 활용 / 보완 / 추가 개발 검토
```

## Why PDF?

BuildWise 전체가 PDF 전용 서비스인 것은 아니다.

첫 번째 PoC만 PDF 문서 검토 업무로 좁혔다.

HIMEC은 설계, PM·CM, 커미셔닝, 데이터센터 등
프로젝트 과정에서 설계도서와 프로젝트 문서를 기반으로
여러 전문 분야와 관계자가 협업하는 업무 특성이 있다.

따라서 가장 기본적으로 접하는 문서 검토 업무부터
AI 활용 판단 구조를 검증한다.

PDF PoC에서는 예시로:

- 가격
- OCR
- 출처 인용
- 사용/처리 조건

등을 비교하지만,
이 항목들이 BuildWise 전체의 고정 Schema는 아니다.

향후 다른 업무에서는 Requirement Schema를 바꿔 재사용한다.

예:
음성 AI라면
분당 비용 / 화자 분리 / 실시간 처리 / 언어 지원 등이 될 수 있다.

단, 현재 프로토타입 개발 범위는 PDF에 집중한다.
음성 등은 확장 가능성 예시로만 사용한다.

## 현재까지 완료한 데이터 PoC

기존 mini3 프로젝트에서 실제로:

- PDF AI 원본 27개 수집
- 원본 데이터 보존
- 가격·기능 정제
- 비교 가능한 데이터 14개 구성
- 가격 분포 분석
- 출처 인용 기능별 비교
- 웹용 `data/data.json` 생성
- GitHub 공개 저장소 구성

까지 완료했다.

현재 데이터 작업은
“BuildWise 판단에 필요한 시장 데이터를
수집하고 구조화할 수 있는가?”를 확인한 단계다.

아직 최종 제품 검증이 끝난 것은 아니다.

## Traceable Decision Data

BuildWise에서는 AI가 결과만 말하는 것이 아니라
판단 근거를 다시 확인할 수 있어야 한다.

현재 적용한 원칙:

- 원본 데이터 별도 보존
- 수집 시점 기록
- 상세 출처 URL 유지
- 정제 전 / 정제 후 데이터 분리
- 정제 규칙 기록
- 웹 제공용 데이터 별도 구성
- 판단에 사용한 원문으로 다시 이동 가능

현재 데이터 흐름:

```
raw.csv
→ clean.csv
→ data.json
→ Decision + 근거 URL
```

핵심 원칙:

> “개인의 검색 결과를 바로 AI 판단에 넣지 않고,
> 출처를 보존하고 비교 가능한 데이터로 구조화한 뒤
> 판단에 사용한다.”

## Prototype v1 적용 우선순위

이 문서의 아래 프로토타입 설명에는
장기 제품 방향이 함께 포함되어 있다.

현재 Prototype v1의 실제 구현 규칙은 아래 문서를 우선한다.

- `PROTOTYPE_V1_DECISION_RULES.md`
- `PROTOTYPE_V1_DECISION_REPORT.md`
- `PROTOTYPE_V1_IA_DESIGN.md`
- `WIREFRAME_01` ~ `WIREFRAME_05`

문서 간 내용이 다를 경우,
현재 v1에서는 위 문서들의 최신 규칙을 따른다.

### 현재 v1 핵심

v1 입력:

- 월 예산
- 출처 인용 필요 여부
- OCR 필요 여부

v1에서 입력하지 않는 항목:

- 업무 목적
- 월 사용량
- 사용자 수
- 다중 PDF 비교

v1 상태:

- 충족
- 확인 필요
- 예산 초과

v1 판단:

- 기존 솔루션 활용 후보 있음
- 기존 솔루션 + 추가 확인 필요
- 현재 조건에서 후보 없음
- 추가 개발 검토는 v1에서 확정하지 않음

## 앞으로 만들 프로토타입

프로토타입은 최소한 아래 흐름이 실제로 동작해야 한다.

1. 업무 조건 입력
2. 기존 PDF AI 후보와 조건 비교
3. 충족 / 미충족 Gap 표시
4. 결과를
   - 기존 솔루션 활용
   - 기존 솔루션 + 보완
   - 추가 개발 검토

   로 구분
5. 판단 이유와 근거 URL 표시
6. 최종 Decision Report 제공

중요:
제품을 먼저 추천하는 구조가 아니다.

```
우리 상황 판단
→ Gap
→ 판단 결과
→ 그 판단에 맞는 후보
```

순서로 보여준다.

## 프로토타입 화면 방향

### STEP 1. 업무 조건 입력

예:

- 업무: 프로젝트 PDF 문서 검토
- 업무량
- 사용자 수
- 예산
- 필수 기능

### STEP 2. 판단 결과

예:

- 기존 솔루션 활용
- 기존 솔루션 + 보완
- 추가 개발 검토

### STEP 3. Gap 분석

각 요구조건별로:

- 충족
- 확인 필요
- 미충족

표시

### STEP 4. 후보 비교

각 제품별로:

- 가격
- 필수 기능 충족 여부
- 부족 기능
- 원문 출처

표시

### STEP 5. Decision Report

사용자가 마지막에 가져갈 수 있는 결과물:

- 업무 조건
- 판단 결과
- 기존 솔루션으로 해결 가능한 영역
- 보완이 필요한 영역
- 추가 개발 검토 영역
- 후보 제품
- 판단 근거 URL

## 제품 가치 검증

현재는 실제 효과 수치를 만들지 않는다.

프로토타입 이후 사용성 테스트를 진행해서
실제 측정한 숫자만 사용한다.

검증할 핵심 지표:

1. 판단 완료 시간
   - 기존 검색/비교 방식
   - BuildWise 사용 방식
2. 판단 명확성
   - 사용자가 활용/보완/개발 방향을 이해했는가
3. 신뢰성
   - 결과의 근거를 확인할 수 있었는가

향후 실제 결과가 나온 뒤에만
“검토 시간 OO% 단축” 등의 수치를 사용한다.

현재 임의 수치는 만들지 않는다.

## 장기 확장 방향

1. 1단계: PDF 문서 검토 PoC
2. 2단계: 업무별 Requirement Schema 확장
3. 3단계: 팀별 AI 도입 판단 기록 축적
4. 4단계: 전사 AI 활용 기준으로 확장

핵심:
PDF AI 추천 서비스가 아니라
“업무 조건과 기존 AI 시장을 비교하는 판단 구조”가
BuildWise의 핵심 자산이다.
