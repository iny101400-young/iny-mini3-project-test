# BuildWise Decision Wireframe

## 1. 화면 목적

사용자가 입력한 조건을 바탕으로
현재 상황을 한눈에 이해하고,
후보와 근거, 추가 확인 항목, 다음 액션까지
한 흐름에서 확인할 수 있게 한다.

제품 목록을 먼저 보여 주지 않는다.

첫 화면에서 가장 먼저 보여야 하는 것은
아래 질문에 대한 답이다.

> "우리 조건에서는 어떤 판단이 나왔는가?"

## 2. Top Summary

화면 최상단에 아래 세 요소를 배치한다.

### 한 줄 판단

가능한 상태:

- 기존 솔루션 활용 후보 있음
- 기존 솔루션 + 추가 확인 필요
- 현재 조건에서 후보 없음

"추가 개발 검토"는 v1에서 확정하지 않는다.

### 입력 조건 요약

예:

| 조건 | 입력값 |
| --- | --- |
| 월 예산 | $10 이하 |
| 출처 인용 | 필요함 |
| OCR | 필요함 |

### 후보 수 요약

반드시 보여 줄 값:

- 전체 비교 후보 수
- 예산 내 후보 수
- 모든 필수 조건이 확인된 후보 수
- 추가 확인 필요 후보 수

숫자는 카드처럼 과도하게 분리하지 않고
한눈에 비교 가능한 형태로 보여 준다.

## 3. Recommended Direction

제목:

- Recommended Direction

목적:

제품 하나를 단순 추천하는 것이 아니라
현재 상황에서 어떤 방식으로 접근하는 것이 적절한지 설명한다.

가능한 방향:

### 기존 SaaS 우선 검토

조건을 명확하게 충족하는 후보가 존재할 때 사용한다.

설명 예시 방향:

> "현재 입력한 조건을 충족하는 후보가 확인됩니다.
> 신규 개발보다 기존 SaaS 검토를 우선하고,
> 도입 전 상세 요금제와 운영 조건을 확인하는 방향이 적절합니다."

### 기존 SaaS 후보 검토 + 추가 확인

일부 필수 조건이 현재 데이터에서 확인되지 않을 때 사용한다.

설명 예시 방향:

> "예산 범위 내 후보가 존재하지만
> 일부 필수 기능은 현재 데이터만으로 확인할 수 없습니다.
> 후보를 제외하기보다 원문에서 해당 조건을 먼저 확인하는 것이 필요합니다."

### 예산 조건 조정 후 재검토

예산 내 후보가 하나도 없을 때 사용한다.

설명 예시 방향:

> "현재 입력한 예산 범위에서는 비교 가능한 후보가 없습니다.
> 기능 부족이나 개발 필요를 의미하지 않으며,
> 예산 조건을 조정한 뒤 다시 비교할 수 있습니다."

중요:

- 현재 데이터에 없는 사실을 만들지 않는다.
- "최적", "최고", "가장 좋은" 같은 검증되지 않은 표현을 사용하지 않는다.
- 사용자의 예산을 자동으로 완화하지 않는다.

## 4. Candidate Comparison

목적:

실무자가 후보 차이를
2~3초 안에 스캔할 수 있게 한다.

표시 항목:

- 제품명
- 가격
- 가격 원문
- Citation 상태
- OCR 상태
- 현재 조건 결과
- 추가 확인 필요 여부
- 원문 출처 링크

상태 표현:

- ✓ 충족
- ? 확인 필요
- ! 예산 초과

중요:

Citation 또는 OCR 정보가 비어 있는 경우
"미지원"으로 표시하지 않는다.

반드시 "확인 필요"로 표시한다.

예산 내 후보가 존재하는 일반 Decision 상태에서는
예산 초과 제품에 "! 예산 초과" 상태를 사용할 수 있다.

모든 제품이 예산을 넘어
"현재 조건에서 후보 없음" 상태가 된 경우에는
Candidate Comparison 자체를 보여 주지 않는다. (9장 참고)

## 5. 후보 정렬 원칙

후보를 임의 점수로 줄 세우지 않는다.

정렬은 아래 우선순위를 사용한다.

1. 모든 필수 조건이 확인된 후보
2. 일부 조건 확인 필요 후보
3. 예산 초과 후보

같은 그룹 안에서는
현재 v1에서 임의의 추천 점수를 만들지 않는다.

현재 v1에서는 별도 정렬 기능을 확정하지 않는다.
위 기본 그룹 순서만 유지하며,
이 순서가 "좋은 제품 순위"처럼 보이지 않게 한다.

## 6. Gap / 추가 확인

제목:

- 추가 확인이 필요한 항목

목적:

"후보가 왜 완전히 확정되지 않았는지"
명확하게 보여 준다.

예:

- Citation 지원 여부 확인 필요
- OCR 지원 여부 확인 필요
- 사용자 수 과금 확인 필요
- 처리 한도 확인 필요
- 조직 보안 / 데이터 정책 확인 필요

중요:

현재 데이터에 없는
사용자 수, 처리 한도, 보안 정책 등은
"추가 확인 필요"로만 표현한다.

지원 여부를 추측하지 않는다.

## 7. Evidence

목적:

사용자가 판단 결과의 근거를
직접 다시 확인할 수 있게 한다.

표시 항목:

- 제품 원문 URL
- 수집 시점
- 가격 원문
- 기능 확인 상태
- 현재 데이터 한계

추가로 현재 표본 기반 EDA 참고 정보를
작은 인사이트 영역으로 보여 줄 수 있다.

### 현재 확인된 사실

- 정제 데이터 14개
- $0 이상 $10 미만 후보 8개
- Citation Yes 그룹 평균 8.46 USD
- Citation No 그룹 평균 20.75 USD
- Citation No 그룹 n=4
- 해당 그룹에 49 USD 값 포함

중요:

이 수치는 전체 시장이 아니라
현재 수집한 표본의 결과라고 표시한다.

EDA는 추천 점수를 만드는 데 사용하지 않는다.
시장 맥락을 이해하는 참고 정보로만 사용한다.

## 8. Next Action

제목:

- 다음으로 확인할 것

사용자가 결과를 본 뒤
바로 무엇을 해야 하는지 보여 준다.

가능한 항목:

- 상세 요금제 확인
- 사용자 수 과금 확인
- 처리 한도 확인
- 조직 보안 / 데이터 정책 확인
- 후보 원문 페이지 확인

현재 데이터로 확인된 항목과
추가로 확인해야 할 항목을 분리한다.

### Report Action

Decision 화면의 결과와 Next Action을 확인한 뒤
자연스럽게 이동할 수 있도록 화면 하단에 둔다.

CTA:

- Decision Report 보기

이 버튼은 `WIREFRAME_05_DECISION_REPORT.md`에서 정의한
Decision Report 화면으로 이동한다.

## 9. Empty State — 현재 조건에서 후보 없음

예산 내 후보가 하나도 없을 때 보여 준다.

제목:

> 현재 조건에서 비교 가능한 후보가 없습니다.

설명:

> "현재 입력한 예산 범위에서는
> 비교 가능한 후보가 없습니다.
>
> 이 결과는 기능 부족이나
> 추가 개발 필요를 의미하지 않습니다."

CTA:

- 예산 조건 다시 입력하기

이 상태에서는 Decision과 Decision Report가 같은 원칙을 사용한다.

- Candidate Comparison을 보여 주지 않는다.
- 빈 표를 보여 주지 않는다.
- 가장 가까운 가격 후보를 보여 주지 않는다.
- 예산 초과 후보를 대체 추천하지 않는다.
- 사용자의 예산을 자동으로 완화하지 않는다.
- 기능 부족이나 추가 개발 필요로 해석하지 않는다.

## 10. 정보 위계

사용자가 읽는 순서:

1. 한 줄 판단
2. 입력 조건 요약
3. 후보 수 요약
4. Recommended Direction
5. Candidate Comparison
6. Gap / 추가 확인
7. Evidence
8. Next Action

제품명보다
판단 결과와 방향이 먼저 보여야 한다.

## 11. Layout 원칙

Desktop 기준:

| 영역 | 구성 |
| --- | --- |
| 상단 | 판단 결과, 입력 조건, 후보 수 요약 |
| 중단 | Recommended Direction, Candidate Comparison |
| 하단 | Gap / 추가 확인, Evidence, Next Action, Report Action |

Candidate Comparison은
표 가독성을 우선한다.

과도한 카드 디자인은 피한다.

상태는 색상 + 아이콘 + 텍스트로 함께 표시한다.

## 12. 사용자가 이 화면에서 느껴야 하는 것

- 그래서 지금 우리 상황에서 무엇을 먼저 해야 하는지 알겠다.
- 어떤 후보가 조건을 충족하는지 빠르게 비교할 수 있다.
- 확인되지 않은 정보가 무엇인지 구분된다.
- 왜 이런 판단이 나왔는지 근거를 확인할 수 있다.
- 결과를 다시 엑셀이나 문서로 정리할 필요가 적다.
- 다음 액션이 명확하다.
